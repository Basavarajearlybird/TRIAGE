# Results: provenance and limits

One section per committed result file: what produced it, what it supports, and
what it does not. Nothing in `data/` is generated by the mock provider; every
file is a record of real API calls.

## Files

### `mtbench_nemotron.json` → `_holdout.json`, `_holdout_multiseed.json`

80 MT-Bench questions, first turns only. Small: `nemotron-nano-9b` (NVIDIA free
lane). Big: `gpt-4o`. Judge: `gpt-4o-mini`, single-answer grading 1 to 10.

Produced by `scripts/mtbench.py`: one free small pass and one paid big pass per
question, then the escalation threshold is swept offline over the stored risk
scores, so the whole curve costs one run. `rows` holds the per-question risk,
both judge scores, and the big-model cost.

The `_holdout` files are recomputed from `rows` by `scripts/mtbench_holdout.py`
at no cost: a 50/50 split by question id, threshold chosen on the tuning half,
reported on the test half with a bootstrap 95% CI, repeated over 5 seeds.

This supports the claim that for this pair, escalating on observed risk saves
most of the big-model bill without losing judged quality, across all 5 splits. It
does not support a precise savings figure. Only 4 to 9 of the 40 test questions
escalate, so the per-split intervals are wide, and the mean across splits carries
more weight than any one split.

### `mtbench_gpt4o.json` → `_holdout.json`, `_holdout_multiseed.json`

Same procedure, small: `ministral-8b`, big: `gpt-4o`. Retired model; it cannot be
re-run as committed (see below).

What this shows is that the pair is a weak test of the router. In 2 of the 5
splits the tuned threshold escalates nothing at all, and the result reduces to
"the small model alone nearly matches GPT-4o on MT-Bench". The 96.0% savings
figure is therefore not evidence that routing works. The savings come from
skipping the big model, and the file says nothing about how well the router calls
it when it does escalate.

### `rigor_gsm8k_multiseed.json`

GSM8K, 5 seeds × 30 items, small: `gpt-4o-mini`, big: `gpt-4o`. Produced by
`scripts/rigor_multiseed.py`, which runs `app/benchmark/rigor.py` once per seed
and pools every item for the significance tests. Each seed samples different
GSM8K items via the global RNG.

Accuracy: always-small 0.947, always-big 0.900, router 0.960. Cost saving against
always-big 85.1% (CI 81.4 to 88.9). Paired bootstrap, router against big: +0.06
accuracy, p = 0.017.

This supports the claim that on this sample the router beat the big model on
accuracy while paying about a seventh of its bill. It does not support a general
claim that routing improves accuracy. The big model scored *below* the small
model here (0.900 against 0.947), so "beats the big model" partly reflects gpt-4o
underperforming gpt-4o-mini on these 150 items. 30 items per seed is small.

### `rigor_gsm8k.json`, negative

GSM8K, 90 items, `ministral-8b` → `gpt-oss-120b`. Retired models.

The router escalated 57.8% of queries and collapsed to 51.1% accuracy while
always-small held 93.3% and always-big 91.1%. Escalating into a big model that
was not better, and doing so on most queries, cost money and accuracy at once.
This is what drove the escalation threshold up and put a floor under the online
controller (`online_learning.risk_high_floor`).

### `rigor_gsm8k_fixed.json`, negative

GSM8K, 30 items, same pair, after that fix. Escalation fell to 13.3% and accuracy
recovered to the small model's 86.7%, but the run cost 29.1% more than
always-big: the remaining escalations added big-model spend without lifting
accuracy. The fix removed the accuracy collapse. It did not make routing pay on
this sample.

### `showtime.json`

30 hand-written queries (12 easy, 10 medium, 8 hard), each billed twice: once
entirely on `gpt-4o`, once through the router with `ministral-8b` as the small
model. Retired model.

$0.0637 to $0.0195, 69.5% saved, 6 escalations, 24 answers at $0.

This shows the shape of the saving on a mixed workload, where easy queries never
reach the paid model. It is not a benchmark claim. The query mix was chosen by
hand and the mix determines the headline, and the file contains no accuracy
measurement at all.

This file also predates a project rename and stores the router's total under the
key `svserve_usd`. It is the same quantity that `scripts/showtime.py` now writes
as `triage_usd`. The value is untouched.

### `ablation.json`, negative

10 labelled prompts × 5 configurations, `llama-3.1-8b` → `nemotron-super-49b`,
entirely on the free lane. Toggles the three optional add-ons on and off.

Accuracy was 0.80 in every configuration, escalation 0 in every configuration,
and dollar cost $0 in every configuration because the lane is free. The only
column that moved was compute: 2176 mean compute units with all three add-ons
against 1521 with none, so on this set the add-ons cost about 43% more compute
and returned nothing.

This supports the claim that the add-ons are not load-bearing for accuracy on a
cold, small, non-repeating prompt set. It does not show that they are useless.
The semantic memory is designed to pay off on repeated or clustered prompts, and
10 cold prompts cannot produce a memory hit worth having. That experiment has not
been run.

## Retired models

`ministral-8b` and `gpt-oss-120b` were removed from `config/models.yaml` after
the runs above. `mtbench_gpt4o.json`, `showtime.json`, `rigor_gsm8k.json` and
`rigor_gsm8k_fixed.json` therefore cannot be regenerated with the current
catalog: they are frozen receipts. Their derived held-out files can still be
recomputed, because those read the committed per-question rows without calling
any model.

Adding catalog entries back would mean supplying provider ids and prices that
cannot be verified from this repository, so they are left out.

The files that can be regenerated end to end, given keys, are
`mtbench_nemotron.json`, `rigor_gsm8k_multiseed.json` and `ablation.json`.

## Experiments not run

MMLU. The harness previously carried an MMLU loader whose network fallback was a
hand-written 12-question sample cycled up to N. No MMLU result was ever produced,
and a fallback that silently substitutes 12 hand-written questions for MMLU can
only produce a misleading number, so the loader was removed. Add a real loader
before making any MMLU claim.

Traps as a standalone dataset. `app/benchmark/rigor.py --dataset traps` works and
2 trap items appear inside `ablation.json`, but no dedicated abstain-axis run is
committed. Unit tests cover the abstain policy; no benchmark result does.

The N=200 head-to-head sweep. A runner existed for
`python -m app.benchmark.rigor --dataset {gsm8k,traps} --n 200 --small gpt-4o-mini
--big gpt-4o --concurrency 6` across datasets. It was never run and produced no
result files, so the runner was removed. The command above is the whole of it.

A repeated-prompt workload for the semantic memory, which is the only setting
where its intended saving could appear.

Calibration of `verify.overhead_tokens`. It is a configured constant of 400
tokens that feeds only the verify cost guard. It was never measured, and no
reported number depends on it.

## Determinism

The embedder was changed from Python's built-in `hash()` to `zlib.crc32` while
this repository was being cleaned up. `hash()` is salted per process, so
retrieval scores, and the similarity-based signals derived from them, differed
between runs of the same experiment on the same input. This changes no committed
number; it makes future runs repeatable. `tests/test_embed.py` checks it by
embedding the same text in a second interpreter.

Everything else that varies between runs is genuine: model sampling, the LLM
judge, and which dataset items a seed draws.
